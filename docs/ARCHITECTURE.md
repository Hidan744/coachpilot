# Архитектура CoachPilot AI

## Обзор

```
Flutter-приложение
 ├─ UI (Riverpod, go_router)
 ├─ Локальная БД Drift/SQLite — источник истины для интерфейса (local-first)
 ├─ Outbox + SyncEngine ─────────────┐
 └─ Таймер, редактор схем             │ HTTPS + JWT
                                      ▼
Backend: FastAPI
 ├─ /auth  /me  /sync  /catalog  /ai  /account
 ├─ AI Gateway: провайдеры (YandexGPT | GigaChat | mock), валидатор планов
 └─ PostgreSQL 16 (SQLAlchemy + Alembic)
Хостинг: облако в РФ (152-ФЗ)
```

## Ключевые решения

1. **Local-first.** Приложение всегда читает и пишет в локальную SQLite; сеть нужна только для
   синхронизации и AI. Поэтому сохранённые планы, библиотека, схемы и таймер работают офлайн.
2. **UUID генерируются на клиенте.** Запись можно создать без сети, и её id не меняется после синхронизации.
3. **План тренировки — документ.** Блоки хранятся JSON-массивом внутри `training_sessions.blocks`:
   правка плана атомарна, конфликт разрешается целиком по занятию. В блок кладётся снимок
   упражнения, чтобы план не зависел от дальнейших правок библиотеки.
4. **Изоляция данных.** У каждой записи есть `owner_id`; сервер фильтрует все чтения и записи по нему,
   ссылки (`team_id`, `player_id`…) проверяются на принадлежность владельцу. `club_id` заложен под клубную версию.
5. **Минимум персональных данных.** У игрока: имя, фамилия (необязательно), год рождения, позиция.
   В AI-запросы персональные данные игроков не передаются.

## Синхронизация

* Каждая запись синхронизируемой сущности имеет `server_seq` — значение глобальной
  последовательности `sync_seq` в момент последней записи на сервере.
* `POST /sync/push` — пачка изменений `{entity, id, op: upsert|delete, base_seq, data}`.
  Каждое изменение применяется в своём savepoint: ошибка одной записи не ломает пачку.
  Результат на каждое изменение: `applied | conflict | rejected`.
* `GET /sync/pull?since=<cursor>&limit=` — все изменения владельца с `server_seq > cursor`, включая удаления.
* Записи одного владельца сериализуются `pg_advisory_xact_lock`, поэтому порядок `server_seq`
  совпадает с порядком коммитов и курсор не пропускает изменения.

### Конфликты

| Сущности | Политика |
|---|---|
| teams, players, favorites, attendance, session_notes, player_assessments | последняя запись побеждает |
| training_sessions, session_reports, drills (свои) | `strict`: если серверная версия новее `base_seq` — конфликт; клиент принимает серверную версию, а свою правку сохраняет копией с пометкой «Конфликт» |
| любая | удаление побеждает правку |

`attendance.id = uuid5(session_id, player_id)` — отметки одного игрока с двух устройств сходятся в одну запись.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | /auth/register, /auth/login | email + пароль (argon2), согласие на обработку ПД обязательно |
| POST | /auth/refresh, /auth/logout | refresh-токены одноразовые (ротация), хранятся хешем |
| GET/PATCH | /me | профиль тренера |
| POST | /sync/push · GET /sync/pull | синхронизация |
| GET | /catalog/drills?version= | системная библиотека упражнений с версионированием |
| GET | /account/export | выгрузка всех данных пользователя |
| POST | /account/delete | удаление аккаунта и всех данных (с подтверждением паролем) |
| POST | /ai/plan, /ai/report | этапы 5 и 7 |
| POST/DELETE | /players/{id}/share | ссылка для игрока и родителей: создать (повторно — та же) / отключить |
| GET | /p/{token} | страница игрока для родителей (HTML, без входа, только данные с пометкой «видно родителям») |

Интерактивная документация — `/docs` (OpenAPI).

## AI-генерация (этап 5)

1. Контекст: параметры занятия и сводка последних отчётов команды (без персональных данных).
2. Кандидаты: 20–40 упражнений из библиотеки, отобранных фильтрами (возраст, игроки, инвентарь, поле, цель).
3. Модель возвращает строгий JSON: блоки с `drill_id` и адаптацией либо новые упражнения (`source: ai`),
   плюс `assumptions[]` и `clarifying_question`.
4. Проверка кодом: схема, сумма минут, совместимость с числом игроков, инвентарь, обязательные поля,
   запрещённые формулировки. При ошибке — одна попытка исправления моделью, затем
   исправление кодом или понятная ошибка.
5. Запасной генератор по правилам работает без сети и без AI.
6. Провайдеры подключаются через общий интерфейс: YandexGPT (основной), GigaChat (запасной), mock (разработка/тесты).

## Сезон: календарь, тактика, развитие игроков, родители

Новые синхронизируемые сущности (тот же механизм push/pull, политика lww):

* `matches` — матчи сезона: соперник, дата, дома/в гостях, стадион, турнир, счёт.
* `schedule_slots` — регулярные тренировки команды: дни недели, время, длительность, место, даты сезона.
  Календарь разворачивает их в занятия по дням (`lib/core/calendar.dart`). Когда тренер открывает
  тренировку из расписания, создаётся план (`training_sessions`) на эту дату и время — он заменяет
  «пустую» тренировку в календаре.
* `tactic_boards` — тактические доски: схема поля (вертикальное `full_v` или горизонтальное `full`),
  расстановка, подписи «номер|Фамилия», стрелки по шагам, линии от руки (`pen` с точками), заметки и замены.
* `development_plans` — индивидуальные планы игрока на неделю/месяц/сезон: цели и задания с отметкой
  выполнения, фокус-навыки, комментарий, флаг «видно игроку и родителям».
* `parent_notes` — сообщения тренера родителям по категориям (питание, психология, доп. тренировки,
  здоровье, дисциплина) с тем же флагом.

Страница для родителей отдаётся сервером по случайному токену (`player_shares`), токен можно отозвать.
На странице — посещаемость, последние оценки, открытые планы и сообщения, расписание и ближайшие матчи
команды. В демо-режиме (без сервера) вместо ссылки тренер копирует готовый текст для мессенджера.
Импорт календаря игр: таблица с колонками «Дата / Время / Соперник / Д/Г / Стадион / Турнир» или
строки вида «15.08 18:00 Зенит (д)», «5 сентября, Амкар — Урал».

## Показатели игроков, ОФП, отчёты

* `match_stats` — статистика игрока в матче (id = uuid5(match_id, player_id)): старт, минуты, оценка 1–10
  и счётчики `stats` — голы, голевые передачи, удары и удары в створ, передачи и точные передачи,
  ключевые передачи, обводки, отборы, перехваты, единоборства, фолы, карточки, сейвы и пропущенные.
  Итоги сезона, точность передач и ударов, показатели за 90 минут считаются в `lib/core/performance.dart`.
  Статистику матча можно загрузить таблицей (Excel/Word/CSV): строка — игрок, колонки узнаются по названию.
* `physical_tests` — тесты ОФП: бег 10 и 30 м, челночный бег 3×10 м, прыжок в длину с места, Yo-Yo IR1,
  наклон вперёд, рост и вес. Результаты переводятся в баллы 0–100 по ориентировочным возрастным нормам
  и рисуют физический профиль (радар: ускорение, скорость, ловкость, мощность, выносливость, мобильность).
* `staff` — тренерский штаб (ассистенты, тренер вратарей, тренер по ОФП, врач, аналитик).
* `development_plans` дополнены ключевой целью и показателями «сейчас → цель» (`targets`), периоды —
  неделя, 4 и 6 недель, месяц, сезон. `session_reports.rpe` — нагрузка по ощущениям: нагрузка = RPE × минуты.

Профиль игрока — вкладки «Обзор» (общий балл, категории, радар навыков, динамика, посещаемость по неделям),
«ОФП», «Развитие», «Статистика», «Родителям». Отчёт о прогрессе («было → стало → следующий шаг»)
выгружается в PDF или картинку; вся отчётность команды — в Excel (игроки, посещаемость, тренировки,
статистика матчей, итоги сезона, ОФП, матчи, штаб). Дашборд команды: посещаемость, нагрузка, ОФП,
результаты, структура нагрузки, лидеры. В демо-режиме «Заполнить примером» создаёт команду с данными.

Схемы упражнений: у игроков и мяча есть постоянный `id`; движение ссылается на игрока (`actor`), пас — на
партнёра (`target`), мяч — на владельца (`holder`). Путь движения — точки, которые тренер ставит на поле.
